⚡ Sumário Executivo

O Family Refresh Token (FRT) é uma vulnerabilidade de design no protocolo OAuth 2.0 implementado pelo Microsoft Entra ID (Azure AD). Ao capturar um único Refresh Token via Device Code Flow, um atacante pode obter Access Tokens válidos para qualquer aplicativo dentro da Family of Client IDs (FOCI) — incluindo Microsoft Office, Teams, OneDrive, Outlook Mobile e Azure CLI — sem interação adicional do usuário.

O ataque não explora falha de software: ele abusa de um comportamento by design do mecanismo de token minting. Um FRT capturado via phishing permanece válido por até 90 dias, dando ao atacante acesso persistente e silencioso ao tenant.

Impacto no ambiente yourdomain.com
Com um único token capturado, o FRT Suite demonstrou acesso a: enumeração de usuários e Global Admins, leitura de emails via Exchange, listagem de arquivos OneDrive, acesso a Teams — tudo sem nova autenticação e sem alertas de MFA.

⚙ Fundamentos Técnicos

Hierarquia de Tokens

O Entra ID emite cinco tipos de tokens com ciclos de vida e capacidades distintas:

Token Validade Propósito Risco
Access Token (AT) 1 hora Autorizar requisições à API Baixo — expira rápido
ID Token 1 hora Autenticação (OpenID Connect) Baixo
Refresh Token (RT) 90 dias (contínuo) Renovar Access Tokens Médio — por app
Family Refresh Token (FRT) 90 dias (contínuo) Renovar AT para qualquer app FOCI CRÍTICO — cross-app
Primary Refresh Token (PRT) Até 90 dias SSO em dispositivos registrados no Entra ID Crítico — device-level

OAuth 2.0 Device Code Flow

O Device Code Flow (RFC 8628) foi projetado para autenticar dispositivos sem browser, como smart TVs. A Microsoft o disponibilizou em todos os clients FOCI. O fluxo de phishing explora exatamente este mecanismo:

# 1. Atacante inicia Device Code Flow para o tenant alvo POST https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/devicecode client_id=d3590ed6-52b3-4102-aeff-aad2292ab01c # Microsoft Office scope=offline_access openid profile https://graph.microsoft.com/.default # Resposta: user_code + verification_uri { "user_code": "G9Z7M", "verification_uri": "https://microsoft.com/devicelogin", "expires_in": 900, "interval": 5 } # 2. Vítima insere código no link enviado pelo atacante # 3. Atacante faz polling e captura o token POST https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/token grant_type=urn:ietf:params:oauth:grant-type:device_code device_code={device_code} # Resposta inclui access_token + refresh_token (FRT)

# Um único RT serve para todos os FOCI clients POST https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token grant_type=refresh_token refresh_token={frt_capturado} client_id={qualquer_client_foci} # troca o app, mesmo token funciona scope=offline_access openid profile https://graph.microsoft.com/.default

Fase 1 — Captura via Device Code Flow

O atacante envia ao alvo um link + código de 5 dígitos (ex: G9Z7M) sob pretexto legítimo (suporte técnico, renovação de senha, MFA setup). A vítima autentica no portal Microsoft real — sem perceber que está autorizando a sessão do atacante.

Implementação: PhishingModule.device_code_flow_real() — polling automático a cada 5s durante 15 min.

Por que o MFA não protege aqui
O Device Code Flow redireciona a vítima ao portal legítimo da Microsoft. A vítima completa o MFA normalmente. O atacante recebe o token com o claim MFA satisfeito, pois a MFA foi feita pela vítima.

Fase 2 — Análise FRT e Expansão FOCI

Com o RT capturado, o FRT Analyzer testa cada um dos 8 clients FOCI, fazendo token minting e populando o Token Vault com um AT por aplicativo. Esta fase tipicamente resulta em 5–8 clients disponíveis em ambientes sem restrições.

Implementação: FRTAnalyzer.analisar_frt() + TokenVault (persiste ATs por client).

Fase 3 — Exploração via Microsoft Graph API

Com ATs válidos para múltiplos apps, o atacante chama a Graph API para reconhecimento:

  • GET /users — enumeração completa de usuários do tenant (paginação automática)
  • GET /directoryRoles/roleTemplateId={roleId}/members — Global Admins, Privileged Role Admins, Security Admins
  • GET /me/messages — leitura de emails (últimos 50)
  • GET /me/drive/root/children — listagem de arquivos OneDrive
  • GET /me/joinedTeams + /channels — estrutura do Microsoft Teams

Fase 4 — Persistência

O BackgroundRenewer é uma daemon thread que verifica a expiração do AT a cada 5 minutos e renova automaticamente 10 minutos antes de expirar. O RT (FRT) se auto-renova a cada uso, reiniciando o contador de 90 dias e garantindo acesso indefinido enquanto não for revogado.

Fase 5 — Escalada Lateral

De posse de acesso ao email e Teams, o atacante pode lançar phishing interno mais convincente, comprometer usuários com mais privilégios, e eventualmente atingir Global Admins para escalada total de privilégio no tenant.

⚠ Indicadores de Comprometimento (IoCs)

  • Device Code Request de IP externo / não corporativo Audit Log → DeviceCodeRequested · Application: Microsoft Office, Azure CLI
  • Burst de renovações para múltiplos FOCI apps em janela <5 min AADSignInEventsBeta · AppDisplayName IN (Office, Teams, OneDrive, Outlook) · UniqueApps ≥ 3
  • Token minting: mais de 10 Refresh Tokens emitidos por minuto para um usuário AADTokenIssuedEvents · TokenType == RefreshToken · Count > 10/min
  • Graph API: leitura em massa de emails (>50 mensagens em 1h) CloudAppEvents · ActionType == Get · ObjectName IN ("messages", "mail")
  • Enumeration de directoryRoles seguida de acesso a dados sensíveis CloudAppEvents · ObjectName == "directoryRoles" → seguido por acesso a mail/files
  • Refresh Token persistindo ativo após >30 dias sem uso na UI Token válido mas sem sign-in no portal — indica renovação programática
  • User-Agent de API / CLI em horário fora do padrão do usuário EvadeModule usa user-agents realistas de apps legítimos — comparar com baseline

🔍 Queries KQL — Microsoft Sentinel / Defender XDR

As queries abaixo são derivadas do KQLModule em frt_suite_extensions.py. Deployar no Microsoft Sentinel (Analytics Rules) ou Defender XDR (Advanced Hunting).

KQL-01 — Device Code Flow Suspeito

Detecta Device Code Requests acima do volume normal
CloudAppEvents | where ActionType == "DeviceCodeRequested" | where Application in~ ("Microsoft Office", "Azure CLI") | summarize Count = count() by UserPrincipalName, IPAddress | where Count > 5

KQL-02 — FRT Testing / FOCI Expansion

Detecta acesso rápido a múltiplos FOCI apps — sinal de token minting
CloudAppEvents | where ActionType == "AuthorizationAttempted" | where ClientAppUsed in~ ( "Microsoft Office", "Microsoft Teams", "OneDrive", "Outlook Mobile", "Office 365 Management" ) | summarize UniqueApps = dcount(ClientAppUsed), Events = count() by UserPrincipalName, IPAddress, bin(TimeGenerated, 5m) | where UniqueApps >= 3

KQL-03 — Token Minting em Burst

Detecta emissão anormal de Refresh Tokens para FOCI apps
AADTokenIssuedEvents | where TimeGenerated > ago(1h) | where ApplicationId in ( "d3590ed6-52b3-4102-aeff-aad2292ab01c", // Microsoft Office "1fec8e78-bce4-4aaf-ab1b-5451cc387264", // Microsoft Teams "ab9b8c07-8f02-4f72-87fa-80105867a763", // OneDrive Sync "27922004-5251-4030-b22d-91ecd9a37ea4" // Outlook Mobile ) | where TokenType == "RefreshToken" | summarize TokenCount = count() by UserPrincipalName, bin(TimeGenerated, 1m) | where TokenCount > 10

KQL-04 — Email Enumeration em Massa

Detecta leitura massiva de emails via Graph API
CloudAppEvents | where ActionType == "Get" | where ObjectName in ("messages", "mail") | where TimeGenerated > ago(1h) | summarize EmailsRead = count(), UniqueIPs = dcount(IPAddress) by UserPrincipalName | where EmailsRead > 50

KQL-05 — Admin Enumeration

Detecta consulta de directoryRoles (típico na Fase 3)
CloudAppEvents | where ActionType == "Get" | where ObjectName == "directoryRoles" | where RawEventData contains "Global Administrator" | where TimeGenerated > ago(1h) | summarize Events = count() by UserPrincipalName, IPAddress | where Events > 1

🛡 Mitigação — Conditional Access Policies

A defesa mais efetiva contra FRT attacks é uma stack de 10 políticas de Conditional Access no Microsoft Entra ID. Aplicadas em conjunto, elas eliminam o vetor de captura, restringem o token minting cross-app e limitam o raio de blast de um token comprometido.

Ordem de implementação recomendada
Implementar na sequência CA001 → CA002 → CA003 → CA006 primeiro (impacto imediato no vetor de ataque). CA004, CA005 e CA010 em seguida. CA007, CA008, CA009 como hardening adicional.

🔄 Revogação de Tokens — Resposta a Incidente

Quando um comprometimento FRT é confirmado, a revogação deve ser imediata. O BackgroundRenewer da suite monitora a cada 5 min — a janela de ação é estreita.

Via Portal Entra ID (imediato)

Sequência
Entra ID → Users → [Usuário afetado] → Authentication methods → Revoke MFA sessions
Em seguida: Users → [Usuário] → Revoke sessions

Via PowerShell (automatizável, recomendado para IR)

PowerShell · Microsoft Graph SDK
# 1. Conectar ao Graph Connect-MgGraph -Scopes "User.ReadWrite.All", "Directory.ReadWrite.All" # 2. Revogar todos os refresh tokens do usuário Revoke-MgUserSignInSession -UserId "andrew.testes@yourdomain.com" # 3. Confirmar revogação Get-MgUser -UserId "andrew.testes@yourdomain.com" ` -Property "SignInSessionsValidFromDateTime" | Select SignInSessionsValidFromDateTime # 4. Resetar senha (forçar logout de todas as sessões) Update-MgUser -UserId "andrew.testes@yourdomain.com" ` -PasswordProfile @{ForceChangePasswordNextSignIn=$true; Password="[nova-senha]"} # 5. Verificar apps com permissões delegadas (possível backdoor) Get-MgUserOauth2PermissionGrant -UserId "andrew.testes@yourdomain.com"

Checklist Pós-Revogação

  • Revogar sessões e MFA sessions no Entra IDEntra ID → Users → Revoke sessions + Revoke MFA sessions
  • Resetar senha e reregistrar MFAForçar re-registro via Authentication methods policy
  • Auditar app permissions delegadasVerificar se o atacante registrou um app com permissões persistentes
  • Revisar Sign-in Logs das últimas 90 diasEntra ID → Sign-in logs → filtrar por usuário comprometido
  • Verificar emails e calendário enviadosExchange Admin Center → Message trace nos últimos 30 dias
  • Checar se há novos dispositivos registradosEntra ID → Devices → filtrar por RegisteredOwner do usuário afetado
